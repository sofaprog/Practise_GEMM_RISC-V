# Контрольные числа из моей проверки (не для диплома)

Эти числа получены не на вашем компьютере и **не вашим компилятором**:
`riscv64-linux-gnu-gcc 13.3` (Ubuntu, glibc), а не `rvv-gcc 13.2` (newlib).
gem5 тот же: форк ValentinV95/gem5, коммит d01492dcd8. Поэтому машинный код
бинарника немного другой, и такты у вас будут отличаться. В диплом идут только
ваши запуски. Эти числа нужны для сверки: если у вас порядок величин или
соотношение ядер сильно другие, что-то настроено не так.

## Что проверено

1. `gem5/spmv_run.py` без параметров и `gem5_board/binary_run.py` на одном
   бинарнике дают побайтно одинаковые `config.ini` и `stats.txt` (все 17
   блоков статистики, кроме строк `host*`).
2. Четыре основных ядра и старое `csr_rvv_slide` проходят проверку результата
   в QEMU при VLEN 128, 256, 512, в том числе с `rvv_ta_all_1s`/`rvv_ma_all_1s`.
   Старое `sellcs_rvv_mem` при VLEN = 128 считает неверно (так и ожидалось:
   оно обрабатывает слайс одним `vsetvl(C)`, а при VLEN = 128 VLMAX = 4 < C = 8). В gem5 основные ядра проходят проверку во
   всех запусках, кроме `--lat gather=1` (см. README, «Известная ошибка gem5»).
3. Все префетчеры запускаются в L1D и в L2. BOP и IMP — только с патчем
   `gem5_patches/prefetch_bop_imp.patch`. Пропатченный gem5 на остальных
   конфигурациях даёт тот же `stats.txt`, что исходный.
4. В серии латентностей такты скалярного ядра постоянны (разброс < 0,03 %).
5. В серии L2 запуски `sms` и `lab` совпадают (это одна и та же конфигурация).

### Латентности (конфигурация лаборатории)

Наибольшая из проверенных латентностей (1, 2, 4, …, 128), при которой векторное
ядро ещё быстрее скалярного CSR. «≥128» — быстрее во всём диапазоне.

| группа | CSR RVV редукция | CSR RVV накопление | SELL-C-σ RVV |
|---|---:|---:|---:|
| gather (vluxei32) | 64 | ≥128 | ≥128 |
| vload (vle32) | 32 | 64 | 64 |
| vec_fp | ≥128 | ≥128 | 64 |
| vec_red | ≥128 | ≥128 | ≥128 |
| vec_misc | 64 | ≥128 | ≥128 |
| vec_all (все сразу) | 16 | 32 | 32 |

С L2 = 2 МБ (`TAG=_l2_2MB EXTRA="--l2-size 2MB"`, значения 1, 4, 16, 64, 128)
nasa2910 целиком помещается в L2, и векторный код проигрывает раньше:
vec_all — после 4 / 16 / 16 тактов, gather — после 16 / 64 / 64,
vec_fp — после 64 / 64 / 16 (порядок ядер тот же, что в таблице).
